# PostgreSQL Migration Design and Implementation Status

**Status (2026-11-13):** PostgreSQL has an implemented psycopg compatibility backend, ordered schema migrations, isolated Docker staging, resumable copy-only import, a separate guarded frozen-snapshot importer, reconciliation, and local restore/fake-worker rehearsals. SQLite remains supported and the standard unit-test backend. This remains **not approved for production**: no live cutover, reverse migration after PostgreSQL writes, operator-managed final backup, production PostgreSQL startup, traffic switch, or AWS worker reconnection has occurred. Run local tests only; paid GitHub Actions are not required.

The compatibility schema retains the current logical schema and text-based IP/payload fields so v1 API and worker contracts can be exercised without changing their representations. Native `INET`/`CIDR`, `JSONB`, query-plan tuning, and workload benchmarks remain follow-up work. Scan exclusions are stored in both SQLite and PostgreSQL and override positive scan authorizations.

## Goals and invariants

- Preserve every existing SQLite row and v1 API behavior. SQLite stays a supported backend during and after migration.
- Public search reads indexed observations immediately and never schedules discovery. Discovery/refresh remains a separate authenticated, bounded admin request handled asynchronously by registered scanners.
- Retain authorization scopes, opt-outs, exclusion lists, worker limits, audit records, bounded retries, and backpressure.
- Do not contact production, copy production credentials, or make a production cutover as part of development.

## Storage model

Use versioned PostgreSQL migrations and repository interfaces, with explicit PostgreSQL SQL and transaction behavior. Avoid pretending SQLite SQL is portable. Use `BIGINT GENERATED BY DEFAULT AS IDENTITY` for surrogate keys, `INET`/`CIDR` for addresses and target ranges, `TIMESTAMPTZ` for event times, `JSONB` for flexible provider payloads, and foreign keys for ownership relationships. Keep stable external IDs and import IDs where they exist.

| Entity | Proposed key and relationships | Important constraints/indexes |
| --- | --- | --- |
| `hosts` | `ip INET PRIMARY KEY`; hostname, ASN, organization, network metadata | GIN/trigram hostname as justified by query plan; B-tree ASN and prefix; first/last seen |
| `services` | identity PK; `host_ip` FK, protocol, port, service/product | unique `(host_ip, port, protocol)`; host and port indexes |
| `banners` | identity PK; `sha256 BYTEA UNIQUE`; canonical bytes/text and encoding | deduplicate exact normalized banner content by SHA-256; retain original data and provenance separately |
| `certificates` | identity PK; SHA-256 fingerprint unique; parsed subject/issuer/SAN/validity and original DER where licensed | exact fingerprint dedupe; expiration and SAN lookup indexes |
| `observations` | identity PK; host/service refs, optional banner/cert refs, source, observed time, provenance, generation | host/time and service/time indexes; append-only history; idempotency key unique per ingest source |
| `workers` | stable worker UUID; hashed token, capabilities, heartbeat, state | unique token hash; heartbeat/availability index; never store bearer token plaintext |
| `scan_generations` | UUID; normalized query, profile, counts, state, requested-by, timestamps | idempotency key unique by requester; bounded scope metadata |
| `scan_tasks` | UUID; generation/host/job refs, state, attempts, next eligible time, lease | unique `(generation_id, host_ip)`; claim index on `(state, available_at, lease_expires_at)` |
| `scan_jobs` | stable v1 job ID, authorization/profile refs, target, port set, worker/lease/result state | retain v1 IDs and state semantics; claim index; idempotent result key unique |
| `authorizations`, `profiles`, `exclusions`, `opt_outs`, `audit_events` | normalized control-plane records and immutable audit trail | CIDR lookup, enabled-state indexes, append-only audit ordering |

`services` represents the latest known service index; `observations` is the historical evidence log. A certificate or banner can be shared across many observations without losing per-host provenance. The implemented compatibility schema preserves current SQLite logical tables through ordered migrations. The proposed native IP/JSON redesign in this section is future work, not part of the current release candidate.

## Ingestion, idempotency, and backpressure

1. Stream the SQLite source through a read-only consistent snapshot in bounded batches. Never load the complete export into memory.
2. Stage each batch with a migration/import UUID and source cursor. Commit the batch and cursor in one transaction so a restart resumes safely.
3. Normalize IP/ASN/protocol/port and canonical banner/certificate bytes before hashing. Use `INSERT ... ON CONFLICT` for host/service upserts and content-addressed banner/certificate deduplication.
4. Give each imported observation a deterministic idempotency identity from source ID (preferred) or a documented stable hash of source, host, service, observed timestamp, and evidence. Preserve duplicates when source semantics represent distinct observations.
5. Bound batch size, transaction duration, pending task count, and ingestion queue bytes. Pause producers when queue/DB thresholds are crossed; expose queue age, retry count, rejected rows, and last committed cursor to admins. Retry transient SQL errors with capped exponential backoff and jitter; reject permanent validation failures with row-level audit output.
6. Do not let indexing enqueue scans. Admin refresh requests select only already-indexed, authorized targets and enforce target/check limits before materializing jobs.

## v1 worker/API compatibility

Keep the current v1 routes, request fields, response fields, worker token authentication, lease token rules, and result idempotency. Put a translation layer at the HTTP boundary and repository methods underneath it. A PostgreSQL deployment must pass the existing worker contract suite unchanged: enroll, heartbeat, claim, start, progress, fail/retry, submit valid results, reject out-of-scope results, cancellation, authorization revocation, and lease expiry. Do not require a simultaneous scanner-agent upgrade.

## Migration and rollback rehearsal

All steps use a disposable copy of a sanitized SQLite database, never a production volume.

1. **Inventory:** run schema/version report, `PRAGMA integrity_check`, table/row counts, min/max timestamps, and deterministic hashes over selected samples. Record SQLite version and source commit.
2. **Expand:** add the PostgreSQL repository and schema migrations while SQLite remains the default and every current SQLite test stays green. Test empty database bootstrap and upgrade from frozen v0.4 and current schemas.
3. **Copy:** use SQLite backup API to make a consistent snapshot, then stream tables in FK order using the resumable batch importer. Keep migration ledger/cursors in the target. Never delete or rewrite the source.
4. **Reconcile:** compare per-table counts, normalized host/service keys, observation time ranges, banner/certificate hashes, worker/job/generation terminal and queued counts, authorization/exclusion/opt-out rows, and selected query result IDs. Require zero unexplained mismatches and PostgreSQL integrity/constraint checks.
5. **Exercise:** run the full unit/API/worker suite against both backends, isolated Docker E2E against PostgreSQL, interruption/resume tests, duplicate/retry tests, and load tests. Verify public search does not enqueue or probe.
6. **Rollback drill:** before cutover, stop writes to the target, retain the untouched SQLite snapshot, switch the staging app back to SQLite, and run integrity plus v1 API/worker smoke tests. For a later write-enabled PostgreSQL rehearsal, freeze writes, export post-cutover changes through a tested reverse mapper, reconcile back into a new SQLite file, validate it, then switch only the disposable staging deployment. Preserve the PostgreSQL snapshot for diagnosis; never overwrite the only SQLite backup.
7. **Cutover gate:** no production cutover is in this project scope. Any later cutover needs a separately approved maintenance window, backup/restore rehearsal, credential/network review, observable rollback point, and operator sign-off.

## Benchmark plan

Create deterministic synthetic datasets with documented generator seed and distributions at 100k, 1m, and (if staging resources permit) 10m observations. Include IPv4/IPv6, common/rare ports, ASN skew, duplicate banners/certificates, and historical rows. Run on declared CPU/RAM/disk and PostgreSQL settings; warm and cold cache separately. Measure rows/sec and MB/sec for imports, WAL/DB growth, duplicate conflict cost, queue lag under producer backpressure, and p50/p95/p99 for exact IP, CIDR, ASN, service/port, hostname, history, facets, and paginated queries. Compare SQLite and PostgreSQL on identical inputs and query semantics; save raw results and `EXPLAIN (ANALYZE, BUFFERS)` plans. Do not claim a speedup without repeatable measurements.

## Future design milestones (not current implementation status)

1. Complete a schema/mapping inventory and backend-neutral query parity review for any future native-type redesign.
2. Consider native PostgreSQL types only after production-size local performance and compatibility benchmarks.
3. Benchmark indexing/search and query plans using synthetic data without production records.
4. Develop and validate a lossless PostgreSQL-to-SQLite reverse migration before any write-enabled production cutover.
5. Publish capacity guidance from repeatable workload measurements.
6. Maintain SQLite as supported. Any production adoption remains a separately approved operation.

## Exit criteria

PostgreSQL support is complete only when schema upgrades, existing-data import, restart/resume, duplicate handling, parity queries, v1 worker compatibility, active-scan authorization, rollback, Docker staging, and benchmark artifacts all pass and are documented. A connection factory or placeholder adapter alone does not satisfy this gate.
